# ممیزی پروژه اولیه و گزارش تغییرات

## جمع‌بندی اجرایی

فایل اولیه یک اسکلت سالم Django 5.2 بود و دو مدل پایه `Customer` و `Project` داشت، اما هنوز یک CRM قابل استفاده محسوب نمی‌شد. تنها URL فعال، فهرست مشتریان بود و همان صفحه نیز بدون ورود، بدون محدودسازی مالک داده و بدون عملیات ثبت/ویرایش/حذف نمایش داده می‌شد.

نسخه جدید هسته همان پروژه را حفظ کرده، اما تمام لایه‌های لازم برای یک محصول داخلی واقعی را به آن افزوده است.

## وضعیت قبل و بعد

| بخش | وضعیت فایل اولیه | وضعیت نسخه حرفه‌ای |
|---|---|---|
| احراز هویت | App خالی؛ صفحه ورود و خروج وجود نداشت | Login/Logout استاندارد Django، POST-only logout و Redirect امن |
| مالکیت داده | `Customer.objects.all()`؛ همه کاربران همه مشتریان را می‌دیدند | تمام QuerySetها با `request.user` محدود شده‌اند |
| مشتری | فقط مدل و یک List ساده | CRUD کامل، جست‌وجو، فیلتر، مرتب‌سازی، صفحه‌بندی و CSV |
| پروژه | فقط مدل؛ بدون URL، View یا Template | CRUD کامل، کنترل بودجه/هزینه/سود/پیشرفت/سررسید و CSV |
| داشبورد | App کاملاً خالی | KPI، قیف فروش، مالی، پروژه‌های اخیر و پیگیری‌های عقب‌افتاده |
| پیگیری فروش | وجود نداشت | تماس، جلسه، ایمیل، بازدید، اولویت، سررسید و تکمیل |
| رابط کاربری | یک HTML ساده و بدون CSS | طراحی RTL حرفه‌ای، واکنش‌گرا، چاپ‌پذیر و مستقل از CDN |
| اعتبارسنجی | صرفاً نوع فیلد مدل | اعتبارسنجی فرم، شماره یکتا برای هر کاربر و نرمال‌سازی رقم فارسی |
| حذف داده | حذف آبشاری مشتری و پروژه | `PROTECT` برای جلوگیری از حذف تصادفی مشتری دارای پروژه |
| امنیت تنظیمات | Secret Key ثابت، Debug روشن و Host خالی | خواندن از محیط، Cookie امن در Production و هدرهای امنیتی |
| تست | فایل‌های تست خالی | ۲۳ تست برای Auth، مالکیت، CRUD، CSV، مدل، Redirect امن و Dashboard |
| داده نمونه | وجود نداشت | فرمان idempotent به نام `seed_demo` |
| مستندات | وجود نداشت | README، معماری، مسیر آموزشی، ممیزی و استقرار |

## ایرادهای مهم نسخه اولیه

### ۱. نشت داده میان کاربران

کد اولیه:

```python
data = Customer.objects.all()
```

این QuerySet بدون توجه به کاربر واردشده تمام رکوردها را برمی‌گرداند. در CRM چندکاربره این یک نقص امنیتی جدی است.

راه‌حل نسخه جدید:

```python
Customer.objects.filter(user=request.user)
Project.objects.filter(customer__user=request.user)
FollowUp.objects.filter(created_by=request.user)
```

علاوه بر فهرست، همین محدودیت در Detail، Update، Delete و Export نیز اعمال شده تا با تغییر دستی ID در URL نتوان به داده کاربر دیگر رسید.

### ۲. نبود لایه Forms

در پروژه اولیه هیچ `forms.py` وجود نداشت. در نتیجه مسیر استاندارد دریافت POST، اعتبارسنجی و نمایش خطا پیاده نشده بود. نسخه جدید از `ModelForm` استفاده می‌کند و یک Mixin مشترک برای ظاهر فیلدها دارد.

### ۳. Appهای نیمه‌کاره

`accounts` و `dashboard` فقط خروجی `startapp` بودند. `projects` نیز مدل داشت ولی URL و View نداشت. در نسخه جدید هر App مسئولیت روشن و URL Namespace مستقل دارد.

### ۴. Secret Key داخل سورس

کلید ثابت داخل Git برای محیط عملیاتی خطرناک است. نسخه جدید مقدار را از `DJANGO_SECRET_KEY` می‌خواند و فایل `.env` را از Git خارج می‌کند.

### ۵. نبود حفاظت حذف

در مدل اولیه، حذف مشتری تمام پروژه‌های او را با `CASCADE` حذف می‌کرد. اکنون رابطه پروژه از `PROTECT` استفاده می‌کند و رابط کاربری نیز قبل از حذف، وجود پروژه را بررسی می‌کند.

### ۶. نبود تست

فایل‌های Test فقط کامنت پیش‌فرض داشتند. اکنون سناریوهای بحرانی مانند IDOR، نشت CSV، مالکیت خودکار، تکراری‌بودن تلفن و تجمیع مالی تست می‌شوند.

## درباره خطاهای رایج قبلی

### `TemplateDoesNotExist: customers/list.html`

در Snapshot پیوست‌شده مسیر فایل درست بود: `templates/customers/list.html` و `TEMPLATES[0]['DIRS']` نیز به پوشه `templates` اشاره می‌کرد. اگر این خطا دوباره رخ دهد، معمولاً یکی از این علت‌هاست:

1. دستور `runserver` بیرون از پوشه‌ای اجرا شده که `manage.py` در آن است.
2. نام پوشه یا فایل با حروف متفاوت نوشته شده است.
3. نسخه دیگری از پروژه در IDE اجرا می‌شود.
4. Template به مسیر دیگری منتقل شده، اما نام آن در `render()` تغییر نکرده است.

برای بررسی:

```bash
python manage.py shell
```

```python
from django.template.loader import get_template
get_template("customers/list.html")
```

### `NameError: models is not defined`

هر فایل مدل باید این Import را داشته باشد:

```python
from django.db import models
```

در نسخه تحویلی تمام مدل‌ها Import صحیح دارند و `python manage.py check` این مورد را پوشش می‌دهد.

## تغییراتی که عمداً انجام نشده‌اند

- API REST اضافه نشده، چون برای هدف آموزشی فعلی باعث ورود زودهنگام یک لایه اضافی می‌شد.
- تقویم شمسی JavaScript اضافه نشده تا پروژه به CDN یا کتابخانه ثالث وابسته نشود.
- پرداخت، فاکتور رسمی و انبارداری خارج از دامنه CRM فعلی نگه داشته شده‌اند.
- دیتابیس PostgreSQL در اجرای محلی اجباری نشده تا شروع کار ساده بماند.

این موارد در انتهای مسیر آموزشی به‌عنوان توسعه مرحله بعد پیشنهاد شده‌اند.
